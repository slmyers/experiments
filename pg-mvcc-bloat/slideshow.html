PostgreSQL MVCC Bloat

Understanding Version Pointers and Production Monitoring

The Hidden Problem

PostgreSQL's MVCC system creates version pointers for every row update.

In production workloads, dead tuples accumulate faster than monitoring can detect.

Result: Database bloat that degrades performance silently

MVCC: Multi-Version Concurrency Control

xmin/xmax are version pointers that determine tuple visibility

Version Pointer Lifecycle

Creation

INSERT INTO users (name) 
VALUES ('Alice');
-- xmin = current_txid
-- xmax = NULL

Update

UPDATE users 
SET name = 'Alice Updated'
WHERE id = 1;
-- Old tuple: xmax = current_txid
-- New tuple: xmin = current_txid

Visibility Rules

  • Tuple is visible if xmin is committed and before your transaction
  • Tuple is invisible if xmax is committed and before your transaction
  • Dead tuples have xmax committed but no active transactions can see them

Dead tuples = bloat

How Bloat Accumulates

VACUUM: The Cleanup Process

  • Scans tables looking for dead tuples (checking xmax version pointers)
  • Marks dead tuple space as reusable
  • Updates free space map (FSM)
  • Updates visibility map
  • Can be triggered manually or by autovacuum
-- Manual vacuum
VACUUM VERBOSE users;

-- Check when last vacuumed
SELECT schemaname, relname, last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'users';

Autovacuum Thresholds

-- Key settings
autovacuum_vacuum_threshold = 50      -- Base threshold
autovacuum_vacuum_scale_factor = 0.2  -- 20% of table

-- Autovacuum triggers when:
dead_tuples > threshold + (scale_factor * total_tuples)

-- Example: 1M row table
dead_tuples > 50 + (0.2 * 1,000,000) = 200,050 dead tuples

Problem: In large tables, 200K dead tuples is significant bloat

Dead Tuples Impact on Shared Buffers

Buffer Cache Pollution

  • Dead tuples occupy pages in shared buffers
  • Sequential scans read all pages (dead + live)
  • Index scans must check tuple visibility using version pointers
  • More I/O for same result set

The Math

-- 100K rows, 40% dead tuples
-- Page size: 8KB, ~100 tuples/page

Clean table: 1,000 pages
Bloated table: 1,667 pages

SELECT COUNT(*): 
  Clean: 1,000 page reads
  Bloated: 1,667 page reads
  
67% more buffer cache pressure

Index Bloat: The Hidden Cost

Why Indices Bloat

  • Each UPDATE creates new index entries
  • Old index entries point to dead tuples
  • Index pages don't shrink automatically
  • VACUUM cleans table but index grows
-- Check index bloat
SELECT 
    indexrelname,
    pg_size_pretty(pg_relation_size(indexrelid)) as size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE schemaname = 'public';

Performance Impact

  • Slower index scans (more pages)
  • More buffer cache usage
  • Degraded B-tree balance
  • Index-only scans fail more often

VACUUM doesn't shrink indices - only REINDEX or VACUUM FULL does

VACUUM vs VACUUM FULL

VACUUM (Regular)

  • Marks dead tuple space as reusable
  • Updates FSM and visibility map
  • Table size stays same
  • Non-blocking (mostly)
  • Fast and safe for production
VACUUM users;
-- Reclaims space within pages
-- Does NOT shrink table file

VACUUM FULL

  • Rewrites entire table
  • Compacts all pages
  • Rebuilds all indices
  • Requires AccessExclusiveLock
  • Shrinks table to minimum size
VACUUM FULL users;
-- Blocks ALL queries
-- Time: proportional to table size
-- Use only during maintenance

Regular VACUUM prevents bloat. VACUUM FULL fixes it (but at high cost).

Table Bloat: The Impact of Tuning

The Critical Insight

Default autovacuum showed similar bloat to no autovacuum

But optimal tuning (2% scale factor) keeps bloat under 5%

  • High update frequency overwhelms default settings (20% threshold)
  • Optimal settings trigger vacuum at 2% = ~3,000 dead tuples
  • Frequent small vacuums prevent bloat accumulation
  • Performance remains stable throughout workload

The Monitoring Gap

# Common monitoring query
SELECT 
    n_dead_tup,
    n_live_tup,
    last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'users';

# But this doesn't tell you:
# - Rate of dead tuple accumulation
# - Version pointer churn
# - Bloat trend over time
# - Impact on query performance

Essential Monitoring Metrics

  1. Dead tuple ratio: n_dead_tup / n_live_tup
  2. Dead tuple growth rate: Change over time intervals
  3. Autovacuum frequency: Time since last_autovacuum
  4. Table bloat percentage: Dead space vs total size
  5. Version pointer churn: Transaction ID advancement rate
  6. Vacuum duration: How long cleanup takes

Production Monitoring Checklist

Setup

  • Enable track_counts
  • Set appropriate log_autovacuum_min_duration
  • Monitor pg_stat_user_tables
  • Track bloat queries regularly

Alert Thresholds

  • Dead tuple ratio > 0.1 (10%)
  • No autovacuum in 1 hour
  • Bloat > 30% of table size
  • Vacuum taking > 10min

Autovacuum Tuning: Optimal Configuration

-- Optimal settings for high-update JSONB tables (keeps bloat < 5%)
ALTER TABLE documents_jsonb SET (
    autovacuum_vacuum_scale_factor = 0.02,  -- 2% trigger (vs 20% default)
    autovacuum_vacuum_threshold = 50,
    autovacuum_vacuum_cost_delay = 5,       -- Fast cleanup
    autovacuum_naptime = 10                 -- Check every 10 seconds
);

-- Conservative settings for moderate-update tables
ALTER TABLE users SET (
    autovacuum_vacuum_scale_factor = 0.05,  -- 5% trigger
    autovacuum_vacuum_threshold = 100,
    autovacuum_vacuum_cost_delay = 10
);

-- Monitor the impact
SELECT 
    schemaname, relname,
    n_dead_tup, n_live_tup,
    last_autovacuum,
    ROUND(100.0 * n_dead_tup::numeric / NULLIF(n_live_tup, 0), 1) as bloat_pct
FROM pg_stat_user_tables
WHERE relname IN ('documents_jsonb', 'users');

Key Takeaways

  1. MVCC version pointers create dead tuples on every update
  2. Default autovacuum settings (20%) are too conservative for high-update tables
  3. Optimal tuning (2% scale factor) keeps bloat under 5%
  4. Monitor dead tuple ratios and trends, not just absolute counts
  5. Tune autovacuum per-table based on workload patterns
  6. Frequent small vacuums are better than infrequent large ones

Proactive monitoring + aggressive tuning = stable performance
